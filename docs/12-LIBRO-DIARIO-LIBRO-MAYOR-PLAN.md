# 12 - Libro Diario / Libro Mayor - Implementation Plan

**Goal:** correct, auditable, traceable double-entry accounting on top of the *existing* Postgres ledger (`asientos_contables` + `contabilidad_service.rs`). No new architecture, no new database, no microservices, no event sourcing/CQRS/Kafka. Everything below extends what already exists.

Every file, table, and line number cited here was verified against the current repo (`services/core/src/**`, `services/core/src/bin/migrate.rs`, `apps/web/app/(dashboard)/contabilidad/**`) — nothing in this doc is invented.

---

## 1. Current Architecture Assessment

### 1.1 What already exists (and is correct/reusable as-is)

The system is **not** starting from zero — a real, tested double-entry ledger already exists:

- **`asientos_contables`** (`services/core/src/bin/migrate.rs:404-420`) — one row per debit-or-credit line: `cuenta TEXT, debe DECIMAL, haber DECIMAL, referencia_tipo, referencia_id, fecha, usuario_id`. Indexed by `(tenant_id, fecha)`, `(tenant_id, cuenta)`, and `(referencia_tipo, referencia_id)`.
- **`ContabilidadService`** (`services/core/src/services/contabilidad_service.rs`):
  - `create_asiento_manual` (line 167) — **already enforces double-entry correctly**: rejects entries with fewer than 2 lines, rejects `sum(debe) != sum(haber)`, rejects an all-zero entry. This is real and does not need to be rebuilt.
  - `sincronizar` (line 223) — a reconciliation job that generates ledger lines for Ventas, Compras, Nómina, Gastos, and Adelantos that don't have one yet, using `NOT EXISTS (... referencia_tipo/referencia_id ...)` as its idempotency check.
  - `libro_mayor` (line 125) — `GROUP BY cuenta, SUM(debe), SUM(haber)`.
- **`tests/ledger_invariant.rs`** — a real, passing test that runs a sale + purchase + expense + payroll-advance + payroll-run through `sincronizar` and asserts `SUM(debe) == SUM(haber)` two independent ways, plus an idempotency test (`sincronizar_is_idempotent_and_never_double_posts`). This is the right kind of test and the plan below extends it rather than replacing it.
- **Traceability primitive**: every auto-generated line already carries `referencia_tipo` + `referencia_id` pointing back to the source row (`ventas.id`, `compras.id`, `nomina_periodos.id`, `gastos.id`, `nomina_adelantos.id`). This is 80% of the traceability chain the user wants; it's missing the "which lines belong to the same entry" grouping (see 1.2).
- **Role gating**: `/v1/contabilidad/*` is already restricted to the `CONTADOR` role (`main.rs:175-183`). Reuse as-is.
- **Frontend already has the shape of this feature planned**: `apps/web/app/(dashboard)/contabilidad/periodos/page.tsx` is a "Coming Soon" stub whose own copy says *"El libro mayor ya registra todo por fecha — el bloqueo formal de meses cerrados llega en una fase posterior."* — i.e., the team already anticipated accounting periods as the next step. This plan delivers exactly that.
- **Source-of-truth tables for every transaction type** (verified in `migrate.rs`): `ventas`/`venta_items`, `compras`/`compra_items`, `gastos`, `cliente_abonos` (customer payments), `nomina_periodos`/`nomina_detalles`/`nomina_adelantos`, `movimientos_inventario` (kardex, includes `AJUSTE`), `notas_credito` (returns/credit memos), `caja_movimientos`, `banco_movimientos`. Nothing here needs to be re-modeled — they're all suitable existing structures per the user's own instruction not to duplicate them.

### 1.2 What's missing (the actual gap)

1. **No journal-entry grouping.** `asientos_contables` rows generated by `sincronizar` are only grouped implicitly by sharing the same `(referencia_tipo, referencia_id)` — which happens to work for auto-generated entries. But `create_asiento_manual` (line 167-202) inserts each line with `referencia_tipo = 'MANUAL'` and **`referencia_id` is never set** — manual entries have *no shared identifier at all*. You cannot fetch "Journal Entry #12345" as one object today; this directly breaks the traceability chain the user asked for (`General Ledger → Journal Entry #12345 → Sale #INV-10025`).
2. **No reversal/immutability mechanism.** Nothing marks an entry as reversed, links a reversal to its original, or prevents a defective posted entry from just sitting there uncorrected. There is also no `void`/`anular` path in `contabilidad_service.rs` at all.
3. **No accounting periods.** Confirmed absent from the schema and confirmed as a known gap by the frontend's own "Coming Soon" stub.
4. **No chart of accounts.** `cuenta` is a free-text `TEXT` column. The account codes ("1100 Caja y Bancos", "4100 Ingresos por Ventas", etc.) are hardcoded string literals inside `sincronizar` (lines 238-336) with no table backing them — no validation, no account type, no way to list "all accounts" without scanning `asientos_contables` for distinct strings that happen to have been used.
5. **Idempotency is app-level only, not DB-enforced.** `sincronizar`'s `NOT EXISTS` check runs inside one transaction, but nothing stops two concurrent calls to `/v1/contabilidad/sincronizar` from both passing the check before either commits (classic TOCTOU). Low probability today (it's a manually-triggered admin action), but not a real guarantee — and the user explicitly asked for "an appropriate idempotency mechanism," not "an idempotency check that works as long as nobody clicks twice."
6. **`libro_mayor` only returns per-account totals** (`SELECT cuenta, SUM(debe), SUM(haber) ... GROUP BY cuenta`), confirmed by the actual frontend table at `apps/web/app/(dashboard)/contabilidad/libro-mayor/page.tsx:82-101` — columns are exactly `Cuenta | Debe | Haber | Saldo`, one row per account. There is **no drill-down to the movement list with a running balance** the user asked for ("Show me every accounting movement affecting this account" with a running `Balance` column). There is also no dedicated "Libro Diario" endpoint at all — `list_asientos` returns individual debit/credit *lines*, filterable, but not grouped into balanced entries in chronological order the way a diario is presented.
7. **Several real business events never reach the ledger at all:**
   - `cliente_abonos` (customer payments against a FIADO balance) — not processed by `sincronizar`. A customer paying down their tab currently produces **zero journal entries**.
   - `notas_credito` (returns/credit notes) — not processed by `sincronizar`. `ventas_service::create_nota_credito` (line 462) already correctly reverses inventory and `caja_movimientos`, but the *ledger* never records the reversal, so a returned sale's original revenue/ITBIS/COGS entries stay posted forever with nothing to offset them.
   - `movimientos_inventario` with `tipo = 'AJUSTE'` (manual stock adjustments/shrinkage) — never synced.
   - `banco_movimientos` (bank deposits/withdrawals) — never synced.
   - **Cost of goods sold is never posted at all.** `sincronizar`'s ventas loop (line 236-243) posts revenue and ITBIS but no COGS/Inventory leg — `venta_items` doesn't even store a cost, so there's no data to post from. This means the "1200 Inventario" account only ever goes up (from purchases) and never down (from sales), which is not correct double-entry and will never reconcile against real stock value.
8. **One real bug**: `sincronizar`'s ventas loop always debits `"1100 Caja y Bancos"` for the full sale total (line 238), **regardless of `metodo_pago`**. But `ventas_service::create_venta` (line 315-324) already correctly treats a `FIADO` sale differently — it does *not* touch `caja_movimientos` and instead increases `clientes.saldo_pendiente`. So a FIADO sale is currently posted to the ledger as if cash was received, which is wrong: it should debit Accounts Receivable, not Cash.

### 1.3 What is explicitly out of scope / should NOT change

Per your instructions, and because these are separate features the business logic doesn't support today (not accounting bugs to fix):

- **Debit notes** — no `notas_debito` table or logic exists anywhere in `ventas_service.rs` or `compras_service.rs`. There is nothing to hook a journal entry into. Not building a debit-notes feature as part of an accounting-correctness fix.
- **Loans** — no `prestamos` table or logic exists. If/when a loan happens, it's already representable today via `POST /v1/contabilidad/asientos` (the existing manual-entry endpoint: e.g. `Debit 1160 Depósitos Bancarios / Credit 2xxx Préstamo por Pagar`). No new feature needed to satisfy the requirement.
- **Supplier credit / accounts payable** — `compras_service::create_compra` (line 105-220) always pays the full total immediately via `caja_movimientos` (`EGRESO`); there is no `proveedores.saldo_pendiente` and no "buy now, pay later" path, unlike the customer side (which has `clientes.saldo_pendiente` + `FIADO`). Since every purchase is already fully paid at creation time, there is no unpaid supplier balance to journal today — nothing is wrong with the current Compra→Ledger mapping. Adding supplier credit (mirroring the existing `FIADO`/`cliente_abonos` pattern onto `proveedores`) would be a genuine new business capability, not an accounting fix — I've listed it as an optional Phase 2 in section 5 but it is **not required** to make the current system's books correct.
- **Real ISR payroll tax calculation** — `nomina_service.rs:446` currently hardcodes `isr = Decimal::ZERO`. That's a payroll-calculation gap, not a ledger gap — whatever `nomina_detalles.isr` says, `sincronizar` already posts it correctly to `"2200 Retenciones y Descuentos"`. Not touching `nomina_service.rs`'s tax math.
- **TigerBeetle / event sourcing / gRPC** — already dead code (see repo-wide cleanup done alongside this plan). Not relevant to this design and not being reintroduced.
- **Rewriting `ventas_service`, `compras_service`, `caja_service`, `nomina_service` business logic** — every change below to those files is additive (new columns populated, or one new step appended to an existing flow), never a rewrite of existing logic.

## 2. Accounting Model

```
Business Transaction (ventas / compras / gastos / cliente_abonos / nomina_periodos /
                       nomina_adelantos / notas_credito / movimientos_inventario /
                       banco_movimientos / manual)
        │
        ▼
Journal Entry header  →  NEW table `asientos`
  (fecha, descripcion, origen, referencia_tipo/id, reversa_de, periodo_id, usuario_id)
        │
        ▼
Journal Lines  →  EXISTING table `asientos_contables`, unchanged shape
  (cuenta, debe, haber)  +  NEW column `asiento_id` grouping lines into one entry
        │
        ▼
General Ledger  →  EXISTING `libro_mayor` (totals, unchanged) + NEW per-account
                    movement endpoint with running balance
```

Traceability chain this satisfies end-to-end:

```
Libro Mayor row (cuenta "1100 Caja y Bancos", saldo)
   → asientos_contables.asiento_id
      → asientos.id  (fecha, descripción, usuario_id, created_at)
         → asientos.referencia_tipo/referencia_id  →  ventas.id (Sale #INV-10025)
            → ventas.cliente_id  →  clientes  (Customer)
```
"Why does this account have this balance?" = walk that chain backwards from any `asientos_contables` row.

## 3. Database Changes

Everything here is **additive**: new tables, or new nullable/defaulted columns on existing tables. No existing column is renamed, retyped, or dropped; no existing query (`list_asientos`, `libro_mayor`, the frontend pages, `ledger_invariant.rs`) breaks.

### 3.1 New table: `cuentas_contables` (chart of accounts)

The account codes already exist as hardcoded strings in `contabilidad_service.rs::sincronizar` (e.g. `"1100 Caja y Bancos"`). This table formalizes them without changing how `asientos_contables.cuenta` is stored (still `TEXT`, for zero blast radius on existing rows/queries) — the application validates against this table before insert instead of the DB enforcing a hard FK.

```sql
CREATE TABLE cuentas_contables (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id TEXT NOT NULL REFERENCES tenants(rnc) ON DELETE CASCADE,
    codigo TEXT NOT NULL,        -- "1100"
    nombre TEXT NOT NULL,        -- "Caja y Bancos"
    tipo TEXT NOT NULL,          -- ACTIVO | PASIVO | PATRIMONIO | INGRESO | GASTO
    naturaleza TEXT NOT NULL,    -- DEUDORA | ACREEDORA (expected normal balance side)
    activo BOOLEAN NOT NULL DEFAULT true,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE(tenant_id, codigo)
);
CREATE INDEX idx_cuentas_contables_tenant ON cuentas_contables(tenant_id, activo);
```

- **Purpose:** canonical account list per tenant; powers the account picker in the UI and validates `cuenta` strings before an entry is posted.
- **Seed data** (migration, one-time backfill for every existing tenant + on new-tenant registration): the exact set already used by `sincronizar`, plus the additions this plan needs:

| Código | Nombre | Tipo | Naturaleza |
|---|---|---|---|
| 1100 | Caja y Bancos | ACTIVO | DEUDORA |
| 1110 | Cuentas por Cobrar | ACTIVO | DEUDORA |
| 1150 | ITBIS Adelantado | ACTIVO | DEUDORA |
| 1160 | Depósitos Bancarios | ACTIVO | DEUDORA |
| 1200 | Inventario | ACTIVO | DEUDORA |
| 1300 | Anticipos a Empleados | ACTIVO | DEUDORA |
| 2100 | ITBIS por Pagar | PASIVO | ACREEDORA |
| 2200 | Retenciones y Descuentos | PASIVO | ACREEDORA |

### 3.2 New table: `asientos` (journal entry header)

```sql
CREATE TABLE asientos (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id TEXT NOT NULL REFERENCES tenants(rnc) ON DELETE CASCADE,
    fecha DATE NOT NULL DEFAULT CURRENT_DATE,
    descripcion TEXT NOT NULL,
    origen TEXT NOT NULL,               -- AUTOMATICO | MANUAL | REVERSION
    referencia_tipo TEXT,               -- VENTA | COMPRA | NOMINA | GASTO | ADELANTO |
                                         -- ABONO_CLIENTE | NOTA_CREDITO | AJUSTE_INVENTARIO |
                                         -- BANCO | MANUAL
    referencia_id UUID,
    reversa_de UUID REFERENCES asientos(id),   -- set only on a REVERSION entry
    periodo_id UUID REFERENCES periodos_contables(id),
    usuario_id UUID REFERENCES usuarios(id),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE(tenant_id, referencia_tipo, referencia_id)
);
CREATE INDEX idx_asientos_tenant_fecha ON asientos(tenant_id, fecha DESC, created_at DESC);
CREATE INDEX idx_asientos_reversa ON asientos(reversa_de);
```

- **Purpose:** groups sibling `asientos_contables` lines into one balanced entry; carries entry-level metadata (who/when/why/period); is the reversal linkage point; is the DB-enforced idempotency guard.
- **Why `UNIQUE(tenant_id, referencia_tipo, referencia_id)` is the idempotency mechanism**: Postgres treats each `NULL` in a unique index as distinct, so `MANUAL` entries (`referencia_id = NULL`) are never blocked from each other, while auto-generated entries for the same source row (e.g. the same `venta.id`) can physically only exist once. `sincronizar` and any future real-time posting hook both become `INSERT ... ON CONFLICT (tenant_id, referencia_tipo, referencia_id) DO NOTHING` — a real DB guarantee instead of an app-level `NOT EXISTS` race.
- **Validations:** `origen` restricted to the 3 values above (`CHECK` constraint); `reversa_de` only settable when `origen = 'REVERSION'`; a `REVERSION` entry's lines must be the original entry's lines with `debe`/`haber` swapped (enforced in `ContabilidadService`, not the DB — matching how `create_asiento_manual` already validates in Rust, not SQL).

### 3.3 New table: `periodos_contables` (accounting periods)

Deliberately minimal — month-level granularity, open/closed only (no sub-period locking, no partial closes):

```sql
CREATE TABLE periodos_contables (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id TEXT NOT NULL REFERENCES tenants(rnc) ON DELETE CASCADE,
    anio INT NOT NULL,
    mes INT NOT NULL,               -- 1-12
    estado TEXT NOT NULL DEFAULT 'ABIERTO',  -- ABIERTO | CERRADO
    cerrado_at TIMESTAMPTZ,
    cerrado_por UUID REFERENCES usuarios(id),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE(tenant_id, anio, mes)
);
CREATE INDEX idx_periodos_tenant ON periodos_contables(tenant_id, anio DESC, mes DESC);
```

- **Purpose:** answers "is this date locked?" Any insert into `asientos` (manual, sync, or reversal) looks up (or lazily creates, in `ABIERTO` state) the `(anio, mes)` row for the entry's `fecha`; if `estado = 'CERRADO'`, the insert is rejected with a clear error. Reversals must be dated in a currently-open period — you fix a closed period's numbers with a new entry today, never by touching the closed period.
- **Closing a period** (`POST /v1/contabilidad/periodos/:id/cerrar`) just flips `estado` and stamps `cerrado_at`/`cerrado_por`; it does not need to recompute or snapshot anything, since balances are always derived live from `asientos_contables` (see §"Performance" in section 7).

### 3.4 Modify existing table: `asientos_contables`

```sql
ALTER TABLE asientos_contables ADD COLUMN asiento_id UUID REFERENCES asientos(id) ON DELETE CASCADE;
CREATE INDEX idx_asientos_contables_asiento ON asientos_contables(asiento_id);
CREATE INDEX idx_asientos_contables_cuenta_fecha ON asientos_contables(tenant_id, cuenta, fecha, created_at);
```

- Nullable at first (backward compatible with any row inserted before this migration), then backfilled (see 3.6) and made `NOT NULL` in a follow-up migration once backfill is verified.
- **Nothing else about this table changes.** `cuenta`, `debe`, `haber`, `fecha`, `referencia_tipo`, `referencia_id` all stay exactly as they are today — `list_asientos` and `libro_mayor` keep working unmodified.

### 3.5 Modify existing table: `venta_items` (for COGS)

```sql
ALTER TABLE venta_items ADD COLUMN costo_unitario DECIMAL(12,2);
```

- Mirrors the pattern `compra_items.costo_unitario` already uses. Nullable, so it doesn't break anything for historical rows.
- **Service change** (not a rewrite): `ventas_service::create_venta` (`services/core/src/services/ventas_service.rs:171-179`) already `SELECT`s `productos.costo` in its per-item loop (needed today for the stock check) — bind that same value into the new column on the existing `INSERT INTO venta_items` (line 278-295). One extra bound parameter, zero new queries.
- This gives `sincronizar` real, sale-time cost data to post COGS against, instead of guessing from today's (possibly since-changed) `productos.costo`.

### 3.6 Migration / backfill notes

- `cuentas_contables`: seed the table above for every row in `tenants`.
- `asientos` header backfill for existing `asientos_contables` rows: group existing rows by `(tenant_id, referencia_tipo, referencia_id)` for anything with `referencia_id IS NOT NULL` (this is exactly how `sincronizar` already inserts them — one call, one transaction, shared reference) and create one `asientos` header per group, `origen = 'AUTOMATICO'`. For pre-existing `MANUAL` rows (no shared id today), group by `(tenant_id, descripcion, fecha, usuario_id, date_trunc('second', created_at))` as a best-effort reconstruction — document this as best-effort in the migration's comment, same style as the existing `migrate.rs` comments explaining non-obvious backfills.
- `periodos_contables`: no backfill needed — rows are created lazily (`ABIERTO`) the first time an entry lands in a given month; historical months stay implicitly open unless someone explicitly closes them later.

## 4. Transaction Rules

All accounts below are exactly the codes in §3.1. This table is the source of truth `sincronizar` (and any future real-time posting) must implement.

| Business Event | Source Table | Debit | Credit | Notes |
|---|---|---|---|---|
| Cash/card/transfer sale | `ventas` (`metodo_pago != FIADO`) | 1100 Caja y Bancos (total) | 4100 Ingresos por Ventas (subtotal) + 2100 ITBIS por Pagar (itbis, if > 0) | unchanged from today |
| Credit sale (fiado) | `ventas` (`metodo_pago = FIADO`) | **1110 Cuentas por Cobrar** (total) | 4100 Ingresos por Ventas (subtotal) + 2100 ITBIS por Pagar (itbis) | **fixes the bug in §1.2.8** — branch on `metodo_pago` instead of always debiting Caja |
| Cost of goods sold (every sale, both cases above) | `venta_items` × `costo_unitario` | 5050 Costo de Ventas | 1200 Inventario | new leg, §3.5; skip if `costo_unitario IS NULL` (pre-migration historical sale) and flag it in the sync result count so it's visible, not silently wrong |
| Customer payment (abono) | `cliente_abonos` | 1100 Caja y Bancos (or 1160 if `metodo_pago` indicates bank) | 1110 Cuentas por Cobrar | new — currently unsynced |
| Purchase | `compras` | 1200 Inventario (subtotal) + 1150 ITBIS Adelantado (itbis) | 1100 Caja y Bancos (total) | unchanged — every purchase is already fully paid in cash today, see §1.3 |
| Operating expense | `gastos` | 5210/5220/5230/5290 by `categoria` | 1100 Caja y Bancos | unchanged |
| Payroll advance approved | `nomina_adelantos` (`estado IN APROBADO, DESCONTADO`) | 1300 Anticipos a Empleados | 1100 Caja y Bancos | unchanged |
| Payroll run | `nomina_periodos` + `nomina_detalles` | 5100 Gasto de Nómina (bruto) | 1100 Caja y Bancos (neto) + 2200 Retenciones (tss+isr) + 1300 Anticipos (liquidación) | unchanged |
| Return / credit note, cash or card sale | `notas_credito` → `ventas.metodo_pago != FIADO` | 4100 Ingresos por Ventas (subtotal) + 2100 ITBIS por Pagar (itbis) + 1200 Inventario (cogs restored) | 1100 Caja y Bancos (total) + 5050 Costo de Ventas (cogs) | **new** — full reversal of the original sale's entry, see §5 step 5; account picked from the *original venta's* `metodo_pago`, not from `caja_movimientos` (which has a pre-existing bug of always crediting Caja even for FIADO returns — not fixed here, out of scope, see §5 note) |
| Return / credit note, fiado sale | `notas_credito` → `ventas.metodo_pago = FIADO` | 4100 Ingresos por Ventas + 2100 ITBIS por Pagar + 1200 Inventario | **1110 Cuentas por Cobrar** + 5050 Costo de Ventas | same as above but credits AR instead of Cash |
| Inventory adjustment, found stock | `movimientos_inventario` (`tipo=AJUSTE`, `cantidad > 0`) | 1200 Inventario | 4200 Otros Ingresos | valued at `costo_unitario` if present, else current `productos.costo` (flagged assumption) |
| Inventory adjustment, shrinkage | `movimientos_inventario` (`tipo=AJUSTE`, `cantidad < 0`) | 5295 Ajuste de Inventario (Merma) | 1200 Inventario | same valuation note |
| Bank deposit | `banco_movimientos` (`tipo=DEPOSITO`) | 1160 Depósitos Bancarios | 1100 Caja y Bancos | assumes a deposit moves cash from the drawer into the bank — flagged assumption, confirm with the business owner if some deposits come from outside the drawer |
| Bank withdrawal | `banco_movimientos` (`tipo=RETIRO`) | 1100 Caja y Bancos | 1160 Depósitos Bancarios | mirror of above |
| Manual / correction entry | user input | as specified by user | as specified by user | unchanged — `create_asiento_manual` already validates balance |
| Reversal | any of the above | mirrors the original entry with debe/haber swapped | — | see §5 step 6 |

Debit notes, loans, and supplier-credit purchases are intentionally absent from this table — see §1.3.

## 5. Implementation Plan

Ordered so each step is independently shippable and testable; nothing here requires the next step to be "done" to be correct in isolation.

**Step 1 — Migration: chart of accounts, journal header, periods.**
- File: new `services/core/src/bin/migrate.rs` block (append to the existing `sqlx::raw_sql(...)` string — same pattern as every other module in that file).
- Adds `cuentas_contables`, `asientos`, `periodos_contables`; `ALTER TABLE asientos_contables ADD COLUMN asiento_id`; `ALTER TABLE venta_items ADD COLUMN costo_unitario`.
- Seed `cuentas_contables` for every existing tenant (`INSERT ... SELECT rnc FROM tenants CROSS JOIN (VALUES (...))`).
- Backfill `asientos` headers + `asientos_contables.asiento_id` for existing rows per §3.6.
- Tests: extend `services/core/tests/` with a migration smoke test that runs `migrate` twice (idempotency of the migration itself — matches the existing `CREATE TABLE IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS` conventions already used throughout `migrate.rs`).

**Step 2 — Chart-of-accounts seeding on new tenant registration.**
- File: `services/core/src/services/auth_service.rs`, inside `register_tenant`, right after the `tx.commit()` removed at line ~264-267 (that spot used to have a dead TigerBeetle comment — this is what actually belongs there now).
- Insert the seed rows from §3.1 for the new `tenant_id`, in the same transaction as tenant/user creation.
- Test: extend the existing tenant-registration test (find via `mod common` helpers already used in `tests/ledger_invariant.rs`) to assert `GET /v1/contabilidad/cuentas` (new, see Step 7) returns the seeded list right after registration.

**Step 3 — `ContabilidadService`: journal-entry grouping + idempotent inserts.**
- File: `services/core/src/services/contabilidad_service.rs`.
- Add a private helper `create_entry(tx, tenant_id, fecha, descripcion, origen, referencia_tipo, referencia_id, usuario_id, lineas: Vec<(cuenta, debe, haber)>) -> Option<Asiento header>` that:
  1. Validates `sum(debe) == sum(haber)` and `>= 2` lines (reuse the exact check already in `create_asiento_manual` lines 168-178 — extract it into a shared function instead of duplicating).
  2. Looks up/creates the `periodos_contables` row for `fecha`; rejects if `CERRADO`.
  3. `INSERT INTO asientos (...) VALUES (...) ## 7. Performance

**Recommendation: keep balances fully dynamic. Do not add a balance/snapshot table now.**

- `libro_mayor` (totals) already computes `SUM(debe)/SUM(haber) GROUP BY cuenta` per request — unchanged, still fine.
- The new per-account running balance (Step 7) is a single indexed window-function query, not a loop or N+1 — Postgres computes `SUM() OVER (...)` in one pass over the rows matched by `idx_asientos_contables_cuenta_fecha`.
- This is a colmado/SME POS, not a high-frequency trading ledger — realistic per-tenant, per-account row counts (thousands to low tens-of-thousands over years) are well within what a single indexed sequential scan handles in milliseconds.
- **If** a specific tenant/account later grows large enough that the running-balance query measurably slows down (this should be observed, not assumed), the natural next step is a small `saldos_cuenta` cache table (`tenant_id, cuenta, saldo, actualizado_hasta`) updated incrementally as new lines are inserted — not a rebuild, just a checkpoint the running-balance query can start from instead of scanning from row 1. **Not building this now** — it would be optimizing a problem that doesn't exist yet, which the user explicitly asked not to do.

## 8. Final Recommendation

In this order:

1. **Migration** (§5 Step 1) — `cuentas_contables`, `asientos`, `periodos_contables`, `asientos_contables.asiento_id`, `venta_items.costo_unitario`. Purely additive; ship this first because everything else depends on it, and it alone breaks nothing.
2. **`ContabilidadService::create_entry` helper + idempotent inserts** (§5 Step 3) — the single choke point every other step routes through. Rewire `create_asiento_manual` onto it first, since it's the smallest, already-tested caller.
3. **Fix the FIADO/Cash bug + add the COGS leg** (§5 Step 4, first half) — these are the two places the *existing* sales flow posts something actually wrong today; fix before adding new coverage on top of a known-wrong base.
4. **Extend `sincronizar`** with the four new loops — abonos, notas de crédito, ajustes de inventario, bancos (§5 Step 4, second half).
5. **Reversal endpoint** (§5 Step 5) — needed by step 4's notas-de-crédito mapping and is the immutability guarantee the user asked for.
6. **Accounting periods** (§5 Step 6) — now that posting paths are consolidated behind one helper (step 2), this is a small addition, not a scattered one.
7. **New read endpoints** — Libro Diario, Libro Mayor drill-down, chart of accounts (§5 Step 7) — the user-facing payoff; do this after the write side is correct, not before.
8. **`venta_items.costo_unitario` capture** (§5 Step 8) — can technically ship any time after the migration, but sequenced last here only because it's the smallest, lowest-risk step and a good place to pause and verify nothing regressed in the POS sale flow before calling this done.

Everything above is additive to the existing schema and existing services; no existing table is dropped or renamed, no existing endpoint's behavior changes except the one bug fix in step 3, and no new infrastructure (queues, event stores, external ledgers) is introduced.
